# How DoseCurve is built

DoseCurve is a static site: plain HTML, CSS and JavaScript with no build step, no framework and no server. Everything
runs in the reader's browser. This page explains how the pieces fit, so a change can be made in the right place.

## The files

| File | What it is | Loaded |
| --- | --- | --- |
| `index.html` | The app: markup, the whole stylesheet (one `<style>`), a small head script (theme, Effects, the opening sequence and link handling, decided before the first paint), the import map for Three.js, and the page's own script (one inline module, about 260 kB) | always |
| `pk-engine.js` | The model: scenarios, the concentration–time solutions, readouts, window statistics, the share-link format, the drug library's numbers, lessons' scenarios, practice kinds' ids. Works in the browser (`window.PK`) and in Node (`require`) | always, `defer` |
| `pk-lessons.js` | The lessons' texts (goal, predict, try this, challenge, why it matters) | when a lesson opens |
| `pk-practice.js` | The practice problem generators and the worksheet builder | when Practice or a problem link opens |
| `pk-glossary.js` | The glossary's terms | when Lessons opens |
| `pk-math.js` | The worked formulas behind each readout | when a readout's working opens |
| `pk-bayes.js` | Bayesian (MAP) individualization from measured levels | when the clinical panel's Bayesian section or a Bayesian case needs it |
| `pk-idr.js` | Indirect response models (Dayneka, Garg and Jusko 1993) | when a scenario uses one |
| `pk-hd.js` | Hemodialysis sessions, exact between events, with one or two compartments (the rebound after each session) | when a scenario uses dialysis |
| `pk-sens.js` | Sensitivity analysis (±20% on each input) and its tornado chart | when its panel opens |
| `pk-tdm.js` | When to sample: the dose from which a repeated regimen is within 10% of steady state, and the model's peak and trough times in that interval | when its section opens |
| `pk-explain.js` | The sentences under "What changed" and in Compare: what moved between two scenarios and why, with the model's numbers | just after the first paint; a link that opens with a baseline waits for it |
| `pk-sources.js` | The drug library's citations | when a drug's sources or a case's references show |
| `cases.js` | The clinical cases, their grading, the case and assignment writers | when Cases or a case link opens |
| `pop-worker.js` | Population mode's virtual patients and percentiles, as a Web Worker (also `require`-able) | when Population is on |
| `stage.js` | The 3D stage (an ES module): the scenario's curve as a ribbon, the opening sequence's scenes, the pill's actions; imports Three.js | after the first paint, outside embeds |
| `validation.html`, `validation/reference.py`, `validation/reference-results.json` | The comparison with an independent SciPy solver, run in the browser on the page and in Node by the tests | the validation page |
| `educators.html` | The educator page, generated by a script from the engine (counts, every lesson's share link, every case's link) | its own page |
| `sw.js` | The service worker: pages from the network first, versioned files from its cache, so the app opens offline after one visit | registered by the app |
| `fonts/` | IBM Plex Sans and Mono (Google's unmodified files, SIL Open Font License) | preloaded |
| `tests/` | `node --test tests/`: the engine, every lesson's claims, every practice answer, every case, the validation comparison, the page's commitments | CI on every push |

## Rules the code keeps

**The engine is the single source of numbers.** The page, the cases, the practice problems, the stage and the
validation page all ask `PK` for every concentration, readout and statistic. The stage draws the very curve the 2D
chart has just sampled (handed over after each render), so the two cannot disagree.

**Files loaded on demand are named by their content hash** (`pk-lessons.js?v=<first 10 hex of its SHA-256>`) in
`index.html`, `sw.js` and `validation.html`, and a test checks every stamp. A new release can never run a page with
an older cached module. After changing one of those files, run `node tools/stamp.js`, which restamps every page;
a test fails until it's done.

**The initial script has a budget:** the inline scripts plus `pk-engine.js` stay within 125% of the Phase 0
baseline (318,996 bytes); a test enforces it. Anything not needed for the first view goes into a lazily loaded file.

**Share links are versioned** (`#v=12&s=…`): older links keep opening exactly what they opened (decoders clamp
values that later ranges allow, such as doses above 2000 mg in links older than v9). Tests decode stored links from
every version.

**Wording is descriptive.** Text never says a regimen is safe, best or recommended; numbers are attributed to their
source or marked "typical value, unverified". Tests scan lesson, practice, case and glossary text for the banned
words.

**Layout never shifts.** Space that a script fills later is reserved (the readouts' rows, the practice problem,
the validation summary), fonts have metric-matched fallbacks, and a link with a `#` part keeps the app invisible
until it has been applied (`html.route-wait`), including the files that link needs: a case's or the case list's
`cases.js`, a lesson's texts, and the explanations for a link that opens with a baseline. Every link kind (each lesson,
each practice kind, worksheet, fit, window and case, and each tab) is checked at 390 and 1440 px before a release.

## The page's script

The inline module in `index.html` is organised in banners (`/* ===== PLOT ===== */` and so on): state, the
controls, the chart (`render()`, which redraws everything that depends on the scenario), the readouts and their
working, the time inspector and Play, the dose timeline, Compare, lessons, practice, fit the data, hit the window,
cases, the library, links and export, the stage hooks, and start-up routing (which link opens what). `render()` is
the one place a change in the scenario flows through; it ends by placing the sliding parts (once per frame), handing
the curves to the stage, and setting the page's tone (dark simulator, paper pages).

## The stage

`stage.js` exports `start(PK)`, which returns `set(data)`, `view(tab)`, `cursor(t)`, `theme()`, `fx()`, `intro()`
and `pill()`. With Effects on and WebGL available it imports Three.js through the import map (pinned to one cdnjs
release, with sha512 integrity for both of its files); otherwise it draws the CSS stage's path and each scene's
SVG frame. It renders only when something changes. Its camera framings and the opening sequence's storyboard are in
[DESIGN.md](DESIGN.md).

## Validation

`validation/reference.py` integrates the same models with SciPy, written from the equations rather than translated
from the engine, and writes `reference-results.json`. `tests/validation.test.js` compares the engine with it in
Node; `validation.html` runs the same comparison in the reader's browser (718 comparisons) and lights its sphere as
each one passes. Regenerate the reference after changing a model: `python3 validation/reference.py`.
