# Decisions during the v1.0 build

Each entry records one judgment call made during the unattended v1.0 run: what was decided, why (one line), and the alternative that was rejected.

| # | Phase | Decision | Why | Rejected alternative |
| --- | --- | --- | --- | --- |
| 1 | – | Follow the v1.0 plan, including Michaelis–Menten kinetics, population variability and a two-compartment stretch goal. | The plan is the owner's latest written direction, and it supersedes the earlier pause on nonlinear and population models. | Keeping the earlier pause and skipping Phases 2 and 6. |
| 2 | – | Push the `v1.0` branch through GitHub's web "Upload files" page. Hashes in `BUILD_LOG.md` are local commits; GitHub gets one upload commit per folder per phase. | This machine has no git push credentials, and the web upload is the write path that already deploys `main`. | Asking for credentials; skipping the branch backups. |
| 3 | – | Put dev tools (Lighthouse 12, numpy, scipy) in a scratch folder outside the repo. | They are for measuring and validation only; the site gains no runtime dependency. | A `package.json` with dev dependencies. |
| 4 | 0 | Stop the font-swap layout shift with metric-matched fallback faces (`size-adjust` and ascent/descent overrides on Arial and Courier New). | CLS fell from 0.144 to 0.01, the fonts look the same, and no new files are needed. | Self-hosting the fonts (more bytes to cache); `font-display: optional` (first visits would often show system fonts). |
| 5 | 0 | Decide the quick-start strip's visibility in the head script, before the first paint. | Un-hiding it from the app script moved the chart after it had been drawn. | Always reserving its space (an empty gap for returning visitors). |
| 6 | 1 | A scenario link without a version is read as version 1, and the old test asserting the opposite was changed. | Ground rule 3 of the plan says a missing version means v1. | Keeping versionless links unreadable. |
| 7 | 1 | The engine is unit-free: a unit system per scenario (mg, mcg, meq) relabels the numbers, and the salt factor S multiplies every dose. Digoxin runs in mcg (so its levels come out in ng/mL) and lithium in mEq/L. | The slider ranges, link clamping and every existing formula stay valid without per-drug special cases. | Internal mg/L with display factors, which would have needed 0.25 mg doses on a 25–2000 mg slider. |
| 8 | 1 | The volume and half-life sliders keep their usual ranges (5–120 L, 0.5–24 h) and widen to 600 L and 72 h only while the value needs it (digoxin). | The fit and window bars mirror these sliders linearly, and a 5–600 L linear slider would be too coarse for everyday use. | A log-scale volume slider (it would break the mirrored sliders). |
| 9 | 1 | Clinical defaults are a 40-year-old man, 175 cm, 70 kg, SCr 0.8 mg/dL (CrCl 121.5 mL/min), with fe = 1 for a custom drug. | Switching the default drug to Clinical then changes clearance by only 1%, so the mode switch itself teaches nothing misleading. | A 65-year-old default (it would shift every curve at the switch). |
| 10 | 1 | Library values follow the FDA label wherever it gives a number, so some profiles changed: amoxicillin t½ 1.2 → 1.0 h; vancomycin t½ 6 → 4.8 h and V 49 → 28 L (0.4 L/kg), now 1 g every 12 h; theophylline V 35 → 31.5 L and 450 mg every 12 h; caffeine V 36 → 42 L. | "Every value has a source" matters more than keeping the old illustrative numbers. The lessons use their own values, so none of their claims moved. | Keeping the old values and flagging them unverified. |
| 11 | 1 | Absorption rate constants (kₐ) are chosen to reproduce the label's time to peak, and the note says so. | Labels give tmax, not kₐ. | Citing kₐ as if the label stated it. |
| 12 | 1 | The gentamicin volume (0.25 L/kg), half-life (2.5 h), phenytoin volume, and ibuprofen and caffeine windows are marked "typical textbook value, unverified". | No accessible label or paper states them in a form I could check. | Citing a textbook page I haven't seen. |
| 13 | 1 | In "What changed", the clearance change is credited to kidney function only when the drug and weight are the same on both sides. | Otherwise, switching drugs would be misread as the renal fraction changing clearance. | Always attributing it to CrCl. |
| 14 | 1 | Added a Kidney function (CrCl) lesson and a matching comparison, beyond what Phase 1 asked for. | Every glossary term must link to a lesson, and the new clinical terms needed one; a tested lesson is also the clearest way to teach Cockcroft–Gault. | Letting glossary terms have no lesson. |
| 15 | 1 | Cases, the validation page and the population worker will be separate files loaded only when used. | After Phase 1 the initial JS is 352,192 bytes (+10.4%), and the budget is +25%. | One growing index.html. |
| 16 | 2 | Saturable elimination is a per-scenario switch (`kin`), and the solution is a dense RK4 run cached per scenario, read by cubic Hermite interpolation. | Every existing consumer of `conc()` (chart, inspector, window statistics, CSV, PNG, comparison) works unchanged, and linear scenarios never touch it. | A separate "nonlinear mode" with its own chart code. |
| 17 | 2 | Vmax is entered per kg per day (the dose's amount unit) and scaled by weight and by organ function or the clinical renal factor; Km is in the concentration unit. | This matches how teaching texts state phenytoin's parameters, and a heavier body or less organ function then means less capacity. | Vmax in mg/h for a 70 kg adult only. |
| 18 | 2 | The predicted Css shown is Km·R / (Vmax − R), exact for a constant input. The simulated steady state (run from that prediction until successive troughs agree) is shown beside it as its swing and average. | Oral doses swing around the constant-input value (phenytoin 300 mg daily averages 2.9% above it), and the plan's "within 1%" holds for a constant input, which the tests check. | Claiming 1% agreement for intermittent doses. |
| 19 | 2 | The time to 90% of steady state is t90 = V·Km·(2.303·Vmax − 0.9·R) / (Vmax − R)², derived here by integrating the model at a constant input, and checked against the simulation. | It can be verified from the model itself, so it needs no outside citation. | Citing a textbook page I haven't seen. |
| 20 | 2 | Phenytoin's Vmax (7 mg/kg/day) and Km (4 mg/L) are marked "typical textbook value, unverified". The label supports only the saturable behaviour and the 10–20 mcg/mL range. | No accessible source I could verify states them. | Citing a textbook without checking it. |
| 21 | 2 | Sheiner–Tozer uses 0.2 × albumin + 0.1, and 0.1 × albumin + 0.1 when the user ticks "End-stage kidney disease". No CrCl threshold is claimed, and the note says references differ (under 10 or under 20 mL/min). | I found both thresholds in secondary sources and couldn't verify a primary one. | Stating one threshold as if it were cited. |
| 22 | 2 | A saturable scenario's all-time AUC is computed only when something reads it, and solutions extend from their last step instead of starting over. | Loading phenytoin took 184 ms before and 16 ms after, well under the plan's 100 ms bound, so no Web Worker is needed. | Moving the saturable path into a worker. |
| 23 | 2 | Nonlinear practice problems run as back-to-back 24 h infusions (a constant input). | That is the case the Css and t90 formulas describe exactly, so each answer can be checked against the simulation to 0.0001%. | Oral dosing, where the formulas are only approximate. |
| 24 | 3 | Cases live in `cases.js`, loaded when the Cases tab first opens and named by content hash like the engine. The service worker precaches that exact file and drops older versions of any `?v=` file. | This keeps the initial JS inside the +25% budget and the cases offline after one visit. | Adding the cases to index.html. |
| 25 | 3 | Each case computes its reference regimen from the patient with the textbook route (its `plan`), then rounds it to practical strengths. The tests check that it passes the case's own grader, and that it moves when the drug's parameters change. | The plan forbids stored answers; a reference computed from the model satisfies that. | Stored reference doses. |
| 26 | 3 | Targets are cited where a source states them: gentamicin peak ≤ 12 and trough ≤ 2 mcg/mL (label), digoxin 0.5–2 ng/mL (label), theophylline 5–20 with peaks above 10 (label), lithium 0.8–1.2 mEq/L at 12 h (label), vancomycin AUC24 400–600 (Rybak 2020, IDSA summary), phenytoin 10–20 mcg/mL (label), the Hartford 7 mg/kg and its CrCl bands (Nicolau 1995 abstract). Gentamicin's peak floor of 5 mg/L is marked a teaching target, unverified. | Those are the sources I could read. | Textbook targets with invented citations. |
| 27 | 3 | The theophylline smoker is modelled as clearance × 1.5 (the label's "about 50%" for young adult smokers), applied by shortening the reference half-life at the same volume. | A cited factor exists, so the case uses it, as the plan allows. | A clearance-slider exercise without a factor. |
| 28 | 3 | In the phenytoin case, Vmax comes from the patient's albumin-adjusted level with Km fixed at 4 mg/L, and the model's levels are read as levels at normal binding. | This is the classic single-level teaching method, and it makes "the low level is an albumin effect" something the student can compute. | A population Vmax that ignores her measured level. |
| 29 | 3 | Lithium's missed-dose effect is computed by superposition at true steady state (the missed dose's own curve taken away). | Lithium's 53 h half-life means a simulated 20-dose regimen hasn't reached steady state. | Reading it off a finite simulation. |
| 30 | 3 | On phones the tab bar scrolls sideways once it has five tabs. | Five labels don't fit 360 px without truncation. | Shortening labels ("Sim", "Prac"). |
| 31 | 4 | The reference is Python (numpy 2.0.2 and scipy 1.13.1, installed in a scratch virtual environment) using `solve_ivp` DOP853 at rtol 1e-11, with the AUC as an extra ODE state and window crossings found by bisection. | Python was available, and an adaptive solver in another language is as independent as it gets from the JS closed forms. | A JS Dormand–Prince integrator (the plan's fallback). |
| 32 | 4 | Tolerances: peak, trough and AUC relative (0.5% first-order, 1% saturable); time in window absolute (0.5 or 1 percentage point). | A relative tolerance on a percentage near 0 would be meaningless. | Relative tolerance on time in window. |
| 33 | 4 | When validation showed `windowStats` up to 0.8% off in AUC and 1 point off in time in window for IV boluses, the engine was fixed rather than the tolerance loosened. Jumps and kinks became samples, and crossings are interpolated. One lesson number changed as a result (0.8 → 0.9 h above MTC; exactly 0.886 h). | The validation exists to catch this. | Widening the tolerance, or leaving the lesson's 0.8 h. |
| 34 | 4 | The validation page reruns the comparison in the reader's browser with the engine the site ships, instead of showing stored pass counts. | Every claim on it is then checked at the moment it is read. | A static report. |
| 35 | 4 | Published worked examples are left out. | None could be checked against an accessible source (the plan says to omit them otherwise). | Textbook examples from memory. |
| 36 | 5 | MIT license, recorded in NEEDS-SAIF for confirmation. | The repository had none, and the plan asks for one; MIT is the common permissive choice for teaching tools. | No license (nobody could reuse the code), or a copyleft license chosen for the owner. |
| 37 | 5 | CI runs `node --test tests/` only; the Python reference is rerun by hand. | The JS suite already compares against the committed reference results, and CI stays dependency-free and fast. | Installing SciPy in CI on every push. |
| 38 | 5 | Visit counting sends `{path: location.pathname}` explicitly, is skipped in `?embed` views, and says on/off in the footer. | This guarantees the # part (scenario settings) and the query never leave, embeds on course pages aren't counted, and the notice states the truth. | GoatCounter's default auto-count. |
| 39 | 5 | README screenshots come from headless Chrome with a throwaway profile, then cropped and quantized to 256 colours (0.53 MB for four). | Playwright wasn't installed, Chrome was, and the user's own Chrome profile stays untouched. | A TODO in place of screenshots. |
| 40 | 5 | Issue templates are Markdown, not YAML forms. | They are simpler to edit, and the Markdown ones work on every GitHub plan. | Issue forms. |
| 41 | 6 | Variability is drawn as CLᵢ = CL·e^ηCL and Vᵢ = V·e^ηV, applied through each patient's volume and half-life, with ω² = ln(1 + CV²) so the CV is the true CV of the log-normal. | The scenario's values stay the medians, and the engine needs no new code path. | Normal (not log-normal) variability, which can go negative. |
| 42 | 6 | ηCL and ηV are independent; there is no covariance. | No sourced correlation was available, and independence is the plainest teaching assumption. | An assumed correlation. |
| 43 | 6 | The population math lives in `pop-worker.js`: a Web Worker in the page, a module in Node. The page passes the engine's stamped address, and the worker loads only a `pk-engine.js?v=<hash>` address. | It is off the main thread and out of the initial payload, and the worker can't be pointed at another script. | Computing on the main thread (up to 0.3 s for 1,000 patients). |
| 44 | 6 | The band is sampled on 241 points across the window, a capped grid; PTA uses each patient's exact steady-state peak and trough. | The band is for looking at, and the PTA needs precision. | A 600-point band (2.5× the work for no visible gain). |
| 45 | 6 | In Compare, A and B use the same seed, so the same virtual patients. | Their difference is then the regimen's, not sampling noise (common random numbers). | Independent draws for A and B. |
| 46 | 6 | Population mode is disabled for saturable scenarios, with a note. | 1,000 RK4 simulations per change would break the responsiveness budget, and the plan allows disabling it. | A slow saturable population. |
| 47 | 6 | PTA is reported only for repeated regimens. | Steady state is defined only there, which is what the plan's PTA is about. | A PTA over the window for single or custom schedules. |

| 55 | 1.1 | Two compartments reuse the V and half-life sliders as V1 and the half-life of k10, with k12 and k21 added. | Switching models then keeps the clearance (k10·V1), so the AUC stays put and the comparison isolates distribution. | New V1/CL sliders that change meaning with the model. |
| 56 | 1.1 | Vancomycin's two-compartment parameters are teaching assumptions: V1 = half of the one-compartment volume, and k12 = k21 = 0.545 h⁻¹, chosen so the terminal half-life is 5.5 h against 4.8 h. | 57 | 1.1 | Two compartments are not combined with saturable elimination: the compartment switch hides when Saturable is chosen, and such a scenario runs as one compartment. | Phenytoin, the saturable example, is taught as one compartment, and a combined path would need a second numerical integrator. | A two-compartment Michaelis–Menten ODE. |
| 58 | 1.1 | The worked formulas (metricMath and its saturable and two-compartment parts) moved to `pk-math.js`, loaded the first time a readout is opened. `PK.metricMath` still loads it on first use in Node. | Two compartments pushed the initial script past +25%. The workings are 17 KB with one consumer, opened on demand. | Raising the budget. |
| 59 | 1.1 | The window statistics became exact rather than sampled: the peak is refined by golden-section search, the area uses Simpson's rule on each smooth step, and MEC and MTC crossings are found by bisection. The last dose's peak uses the same refinement, with every dose and infusion end added to its grid. | The two-compartment validation showed a 0.13% peak gap. The same gap existed with one compartment (up to 1.2% for a short infusion's last peak). The cost is about 1 ms per update. | Loosening the tolerance, or a finer grid (slower, still inexact). |
| 60 | 1.1 | For two compartments, the share of steady state is the full regimen's final trough over the steady-state trough, computed. The time to 90% uses the terminal half-life. | With two exponentials, 1 − e^(−k·nτ) has no single k. | Using k10 (wrong) or β alone (approximate). |
| 61 | 1.2 | Population mode now covers saturable scenarios, reversing decision 46. The variability goes on Vmax (Km fixed) and volume. A virtual patient whose input exceeds their Vmax has no steady state: they count as missing the target, and their share is reported. | Solving the steady state directly and integrating each patient once brought 1,000 saturable patients to about 1 s in the worker. Variability is also where phenytoin's teaching point lies: the same dose leaves some people far above the range. | Keeping it disabled; putting variability on Km too (no sourced CV). |
| 62 | 1.2 | The saturable steady state is found as the fixed point of the one-interval map, by a secant search, instead of simulating blocks of doses until the trough stops moving. | Near Vmax the approach takes thousands of hours, so the block search stopped early (up to 0.12% off, found by comparing the two). The fixed point is exact and about 100× faster. | Tightening the block search (slower still). |
| 63 | 1.2 | A population job that is superseded while running is stopped by terminating the worker and starting a new one. | Workers run jobs in order, so a slider drag would otherwise queue seconds of stale work; restarting costs one cached script load. | Cooperative cancellation inside the worker (the job is one synchronous loop). |
| 64 | 1.2 | The Google Fonts stylesheet is preloaded and switched to a stylesheet on load (with a noscript fallback). pk-engine.js is `defer`, and the app script is an inline `type="module"` script, which is deferred and runs after the engine in document order. | Lighthouse showed both as render-blocking (about 0.8 s each on mobile). A module script needs no new file, and the app was already a strict-mode IIFE with no inline handlers. The filmstrip shows the first frame is already complete, and CLS stays 0. | Moving the app into a separate deferred file (a new stamped file and more churn for the same effect). |
